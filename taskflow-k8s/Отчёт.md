# Отчёт: TaskFlow в Kubernetes (minikube)

Приложение из первого задания — **TaskFlow**, трекер задач: Node.js 22 + Express (REST API и
статический фронтенд) и PostgreSQL 17. В этом задании оно развёрнуто в однонодовом кластере
**minikube** (v1.39.0, Kubernetes v1.37.0, драйвер `docker`, рантайм контейнеров `docker`).

Состав архива:

| Путь | Назначение |
|---|---|
| `app/` | исходники приложения вместе с `Dockerfile` (та же кодовая база, что в задании №1) — образ `taskflow:1.0` собирается прямо из архива |
| `k8s/*.yaml` | манифесты Kubernetes, применяются одной командой `kubectl apply -f k8s/` |
| `scripts/*.sh` | сборка образа внутри minikube, развёртывание, удаление, упаковка архива |
| `README.md` | инструкция по запуску |
| скринкаст | демонстрация запуска, списка подов, масштабирования и работы UI |

## 1. Сборка образа и загрузка в minikube

Образ собирается docker-демоном **внутри** minikube, поэтому отдельный шаг загрузки не нужен —
kubelet видит образ сразу:

```bash
eval $(minikube docker-env)        # docker CLI теперь говорит с демоном minikube
                                   # (fish: minikube docker-env | source)
docker build -t taskflow:1.0 app   # scripts/build-image.sh делает то же самое
```

Альтернативный путь (`scripts/load-image.sh`): собрать образ демоном хоста и загрузить
`minikube image load taskflow:1.0`. В обоих случаях образ лежит только в локальном кеше узла,
поэтому в манифестах стоит `imagePullPolicy: Never` — Kubernetes не пойдёт за ним в Docker Hub.

Образ один и тот же для приложения и для миграций: это один релиз, запускаемый с разными
командами (`node src/server.js` и `node src/migrate.js`).

## 2. Какие абстракции Kubernetes использованы

| Абстракция | Объект | Зачем |
|---|---|---|
| **Namespace** | `taskflow` | изоляция всех объектов приложения от системных; удаление одной командой; метки Pod Security Admission `enforce: restricted` |
| **ConfigMap** | `taskflow-config` | несекретная конфигурация: `PORT`, `NODE_ENV`, `RATE_LIMIT_PER_MINUTE`, имя БД и пользователя, адрес и порт Service БД |
| **Secret** | `taskflow-db-credentials` | пароль PostgreSQL; хранится отдельно от ConfigMap, подаётся в контейнеры через `secretKeyRef` |
| **StatefulSet** | `db` (1 реплика) | PostgreSQL: стабильное имя пода `db-0` и привязанный к нему постоянный том |
| **PersistentVolumeClaim** | `pgdata-db-0` (из `volumeClaimTemplates`) | данные базы переживают пересоздание пода; том выдаёт StorageClass по умолчанию `standard` (hostPath-provisioner minikube) |
| **Service (headless)** | `db`, `clusterIP: None` | DNS-имя `db`, по которому приложение находит PostgreSQL |
| **Deployment** | `taskflow` (2 реплики) | stateless-приложение: масштабирование `kubectl scale`, RollingUpdate с `maxUnavailable: 0`, мягкая anti-affinity между репликами |
| **ReplicaSet** | создаётся Deployment'ом | поддерживает заданное число одинаковых подов |
| **Pod** | `db-0`, `taskflow-*` | единица запуска; у подов приложения два init-контейнера и один основной |
| **Init-контейнеры** | `wait-for-db`, `migrate` | дожидаются готовности базы и применяют миграции до старта сервера |
| **Service (NodePort)** | `taskflow`, `80 → 3000`, nodePort `30080` | единая точка входа и балансировка между репликами; доступ снаружи кластера |
| **Probes** | startup/readiness/liveness `pg_isready`; liveness `/api/health`, readiness `/api/ready` | самовосстановление и исключение неготовых реплик из балансировки |
| **Resources / SecurityContext** | requests и limits у всех контейнеров; non-root, seccomp `RuntimeDefault`, `readOnlyRootFilesystem`, `capabilities: drop ALL` | планирование по ресурсам и минимальные привилегии; профиль `restricted` принудительно проверяется на уровне namespace |
| **Lifecycle hook** | `preStop: sleep 5` | плавный вывод реплики из балансировки при остановке |

### Почему именно так

**StatefulSet для базы, Deployment для приложения.** У PostgreSQL есть состояние на диске и ему
нужна стабильная идентичность: `volumeClaimTemplates` создаёт PVC с именем `pgdata-db-0`, и при
пересоздании пода `db-0` подключается тот же том. Проверено: после `kubectl delete pod db-0` под
поднялся заново, таблицы и строки на месте. Приложение же не хранит состояния (VI фактор), поэтому
его реплики взаимозаменяемы — это и позволяет масштабировать его обычным `kubectl scale`. Базу
масштабировать так нельзя: вторая реплика PostgreSQL без настроенной репликации — это вторая
независимая база.

**Миграции — init-контейнером, а не отдельным Job.** В docker compose порядок «база → миграции →
приложение» задавался через `depends_on`. В Kubernetes между Job и Deployment нет декларативной
зависимости: приложение могло бы стартовать раньше, чем Job закончит. Init-контейнер решает это
строго: основной контейнер не запустится, пока `migrate` не завершится успешно. Раннер миграций
идемпотентен (журнал в таблице `schema_migrations`) и берёт advisory-блокировку PostgreSQL, поэтому
одновременный старт нескольких реплик безопасен — в логах видно, что первая реплика применила
`001_init.sql`, а остальные написали `skip (already applied)`. При масштабировании каждая новая
реплика сама убеждается, что схема актуальна. Обратная сторона: миграция выполняется при старте
каждого пода, в том числе во время RollingUpdate, когда старые реплики ещё обслуживают трафик
против уже изменённой схемы. Это безопасно только для обратно совместимых миграций
(expand/contract: сначала добавить, потом, в следующем релизе, удалить) — такое ограничение обычно и
принимают для развёртываний без простоя.

**`wait-for-db` перед миграцией.** Без него `migrate` падал бы с ошибкой соединения и уходил
в CrashLoopBackOff с растущими паузами (10 с, 20 с, 40 с…), что заметно затягивает первый старт.
Цикл `until pg_isready` ждёт базу с шагом в 2 секунды.

**Headless Service для базы.** У StatefulSet один под, виртуальный IP ему не нужен: имя `db`
резолвится напрямую в IP пода `db-0`. Пока readiness-проба `pg_isready` не прошла, DNS-запись не
публикуется (`publishNotReadyAddresses` по умолчанию `false`) — так приложение не получит адрес
ещё не готовой базы. После пересоздания `db-0` IP меняется, но клиент `pg` резолвит имя при каждом
новом соединении, поэтому пул приложения переподключается сам. У PostgreSQL есть ещё и
`startupProbe` на 150 секунд: первый запуск с `initdb` на медленном диске не будет прерван
liveness-пробой.

**Пробы разделены осознанно.** Liveness `/api/health` не ходит в БД: иначе при кратком сбое базы
kubelet перезапускал бы здоровые реплики приложения. Readiness `/api/ready` делает `SELECT 1`:
при недоступной базе реплика просто выводится из балансировки Service и возвращается, когда база
снова отвечает. Проверено пересозданием `db-0`: поды приложения не перезапускались (`RESTARTS 0`),
после возврата базы readiness снова 200.

**Плавная остановка.** При удалении пода (scale down, RollingUpdate) Kubernetes параллельно
убирает его адрес из Service и шлёт контейнеру SIGTERM; kube-proxy узнаёт об изменении с задержкой
в секунды. Хук `preStop: sleep 5` откладывает SIGTERM, чтобы новые соединения на уходящий под
перестали приходить, а затем сервер сам дожидается завершения активных запросов (обработчик
SIGTERM в `src/server.js`). Без этого часть запросов в момент выкатки получала бы сброс соединения.

**Конфигурация без дублирования.** Пароль задан в одном месте (Secret), имя пользователя и базы — в
ConfigMap. `DATABASE_URL`, которую читает приложение, собирается в манифесте подстановкой
`$(POSTGRES_USER):$(POSTGRES_PASSWORD)@$(DB_HOST):$(DB_PORT)/$(POSTGRES_DB)` — Kubernetes
раскрывает `$(VAR)` для переменных, объявленных раньше в списке `env`. Те же ConfigMap и Secret
использует StatefulSet PostgreSQL, так что учётные данные базы и приложения не разойдутся.

**Secret в репозитории.** В архиве лежит dev-пароль для одноразовой базы внутри minikube. В
реальном окружении Secret создавался бы вне репозитория (`kubectl create secret`, External
Secrets, Sealed Secrets), а манифест в git содержал бы только ссылку на него по имени. Стоит
помнить, что PostgreSQL читает пароль только при инициализации тома: смена значения в Secret у
уже развёрнутой базы не меняет пароль в ней, и приложение перестанет подключаться (см. README).

**Минимальные привилегии принудительно.** Namespace помечен `pod-security.kubernetes.io/enforce:
restricted`: API-сервер отклонит любой под без `runAsNonRoot`, seccomp-профиля, `drop ALL` и
с разрешённым повышением привилегий. У обоих образов корневая ФС контейнера только для чтения;
PostgreSQL для сокета и временных файлов получает `emptyDir`-тома `/var/run/postgresql` и `/tmp`.

## 3. Как сервисы приложения взаимодействуют между собой

```
 браузер на хосте (macOS)
        │  minikube service taskflow  → туннель  http://127.0.0.1:<порт>
        ▼
 узел minikube : NodePort 30080
        │
        ▼
 Service taskflow (ClusterIP <виртуальный IP>:80) ── балансирует по готовым подам
        │                 │                 │
        ▼                 ▼                 ▼
 Pod taskflow-A     Pod taskflow-B     Pod taskflow-C …      (Deployment, N реплик)
   :3000              :3000              :3000
        │                 │                 │
        └─────────────────┴─────────────────┘
                          │  DATABASE_URL = postgres://taskflow:***@db:5432/taskflow
                          │  DNS: db → db.taskflow.svc.cluster.local → IP пода db-0
                          ▼
                 Service db (headless)
                          │
                          ▼
                     Pod db-0 : 5432    (StatefulSet PostgreSQL)
                          │
                          ▼
                 PVC pgdata-db-0  →  PV (hostPath на узле minikube)
```

**Пользователь → приложение.** Запросы приходят на Service `taskflow`. Это NodePort: на узле
открыт порт 30080, внутри кластера у Service есть ClusterIP и порт 80. kube-proxy распределяет
**TCP-соединения** (не отдельные HTTP-запросы) между эндпоинтами Service — всеми подами с меткой
`app.kubernetes.io/name: taskflow`, прошедшими readiness-пробу. При `kubectl scale --replicas=4`
в EndpointSlice появляются четыре адреса, и новые соединения начинают расходиться по четырём
репликам без каких-либо изменений со стороны клиента. Браузер держит keep-alive-соединение, поэтому
серия кликов одного пользователя может уйти на одну реплику; распределение видно на серии
запросов отдельными соединениями (например, `curl` в цикле).

На macOS с драйвером `docker` IP узла minikube недоступен с хоста напрямую, поэтому
`minikube service taskflow -n taskflow` поднимает туннель и открывает браузер на локальном порту.

**Приложение → база.** Приложение знает о базе только строку `DATABASE_URL` (IV фактор:
сторонняя служба как прикреплённый ресурс). Хост в ней — `db`, короткое имя Service в том же
namespace; кластерный DNS (CoreDNS) раскрывает его в `db.taskflow.svc.cluster.local` и, поскольку
Service headless, отдаёт IP пода `db-0`. Соединение идёт напрямую под → под по сети кластера на
порт 5432. Каждая реплика приложения держит собственный пул соединений (до 10), то есть с ростом
числа реплик растёт и число соединений к базе — ограничение, которое нужно учитывать при
масштабировании.

**Миграции → база.** Init-контейнер `migrate` ходит в ту же базу по той же `DATABASE_URL`, что и
приложение, но запускается раньше основного контейнера и один раз на под.

**База → том.** PostgreSQL пишет в каталог `/var/lib/postgresql/data/pgdata` на томе
`pgdata-db-0`. Это единственное хранилище состояния во всей системе: приложение и его реплики
ничего не хранят локально (у контейнера приложения корневая ФС вообще только для чтения).

**Что с чем *не* взаимодействует.** Реплики приложения не общаются друг с другом: нет общего
кеша, сессий или очередей, вся разделяемая информация — в PostgreSQL. База не доступна снаружи
кластера: у Service `db` нет NodePort. Внутри кластера она достижима из любого пода по DNS-имени
`db.taskflow.svc.cluster.local` — единственный барьер здесь пароль из Secret; чтобы ограничить
доступ только подами приложения, понадобилась бы NetworkPolicy и CNI, который её применяет
(в minikube по умолчанию такого нет).

## 4. Отличия от docker compose из задания №1

| docker compose | Kubernetes | Комментарий |
|---|---|---|
| сервис `db` + volume `pgdata` | StatefulSet `db` + PVC | том привязан к идентичности пода, а не к имени volume |
| сервис `migrate` + `depends_on: service_completed_successfully` | init-контейнер `migrate` | порядок гарантируется внутри пода, а не на уровне оркестратора |
| `depends_on: service_healthy` | init-контейнер `wait-for-db` + readiness-пробы | в Kubernetes нет зависимостей между workload'ами |
| сервис `app` с `ports: 127.0.0.1:3000` | Deployment + Service NodePort | реплик несколько, вход через Service, а не через порт контейнера |
| `environment:` с подстановкой `${VAR}` | ConfigMap + Secret + `$(VAR)` в `env` | секреты отделены от обычной конфигурации |
| `restart: unless-stopped` | ReplicaSet + liveness-проба | под пересоздаётся контроллером, а не демоном Docker |
| `healthcheck` в Dockerfile | `livenessProbe`/`readinessProbe` в манифесте | Kubernetes игнорирует `HEALTHCHECK` образа (cri-dockerd его даже не запускает — у контейнеров в `docker ps` нет статуса healthy); пробы задаются в Pod spec |

## 5. Как проверить

```bash
minikube start --driver=docker --container-runtime=docker
scripts/build-image.sh                        # образ taskflow:1.0 внутри minikube
kubectl apply -f k8s/                         # запуск приложения и зависимостей
kubectl get pods -n taskflow -w               # db-0 → Running, taskflow-* → Init → Running
kubectl get all,pvc -n taskflow
kubectl scale deployment/taskflow -n taskflow --replicas=4
kubectl get endpointslices -n taskflow -l kubernetes.io/service-name=taskflow
minikube service taskflow -n taskflow         # UI в браузере (блокирует терминал — туннель)
kubectl delete pod db-0 -n taskflow           # данные переживают пересоздание пода базы
kubectl logs -n taskflow -l app.kubernetes.io/name=taskflow -c taskflow --prefix --tail=5  # запросы по репликам
scripts/destroy.sh                            # удалить namespace вместе с томом
```

Результат на момент написания отчёта: три пода `Running` после `kubectl apply`, миграция
применена один раз (`apply 001_init.sql`), остальные реплики её пропустили, после
`kubectl scale --replicas=4` в Service четыре готовых эндпоинта, UI создаёт проекты и задачи,
данные сохраняются после пересоздания пода базы.
