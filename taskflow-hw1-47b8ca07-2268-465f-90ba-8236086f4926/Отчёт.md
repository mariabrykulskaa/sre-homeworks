# Отчёт: TaskFlow — приложение 12 факторов

## 1. Доменная область

**TaskFlow** — трекер задач по проектам. Пользователь создаёт проекты, внутри каждого проекта ведёт задачи, двигает их по статусам (`к работе → в работе → готово`), фильтрует по статусу, редактирует и удаляет. Доменная область выбрана намеренно компактной: она даёт содержательные CRUD-операции и связь «один-ко-многим» между сущностями, но не перегружает приложение логикой — это пригодится для последующих домашних заданий (контейнеризация, балансировка, масштабирование).

## 2. Стек реализации

| Слой | Технология | Почему |
|---|---|---|
| Бэкенд | Node.js 22 + Express 5 | Нетребователен к ресурсам, мгновенный старт, REST «из коробки» |
| Протокол | HTTP/1.1, REST, JSON | По рекомендации из задания (без gRPC — не будет проблем с балансировкой) |
| СУБД | PostgreSQL 17 | По требованию задания; доступ через `pg` (пул соединений, параметризованные запросы) |
| Фронтенд | HTML + CSS + ванильный JavaScript | SPA на одной странице без сборки — минимум ресурсов и зависимостей |
| Миграции | Собственный раннер (`npm run migrate`) | SQL-файлы, журнал в таблице `schema_migrations`, транзакционное применение |
| Контейнеризация | Dockerfile + docker compose | Одинаковое окружение локально и в проде |
| Тесты | встроенный `node:test` | Юнит-тесты валидации + интеграционные тесты API против тестовой БД |

Зависимостей всего четыре: `express`, `pg`, `dotenv`, `express-rate-limit`. Шрифты фронтенда самостоятельно хостятся в `public/fonts/` — у приложения нет недекларированных внешних зависимостей времени выполнения (CDN и т. п.).

## 3. Основные сущности

### Project (проект)

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | BIGINT IDENTITY | первичный ключ |
| `name` | TEXT | 1–120 символов, обязательное |
| `description` | TEXT | до 2000 символов |
| `created_at`, `updated_at` | TIMESTAMPTZ | ставятся автоматически |

### Task (задача)

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | BIGINT IDENTITY | первичный ключ |
| `project_id` | BIGINT | FK → `projects.id`, `ON DELETE CASCADE` |
| `title` | TEXT | 1–200 символов, обязательное |
| `description` | TEXT | до 5000 символов |
| `status` | TEXT | `todo` / `in_progress` / `done` (CHECK-ограничение) |
| `created_at`, `updated_at` | TIMESTAMPTZ | ставятся автоматически |

Связь: один проект — много задач. Все ограничения продублированы на двух уровнях: валидация на входе в API (`src/lib/validate.js`) и ограничения СУБД (CHECK, FK, NOT NULL).

Над обеими сущностями реализован полный CRUD (см. таблицу эндпоинтов в `README.md`).

## 4. Соответствие 12 факторам

### I. Кодовая база (Codebase)

> Одна кодовая база в системе контроля версий — много развёртываний.

Весь код (бэкенд, фронтенд, миграции, инфраструктурные файлы) живёт в одном git-репозитории. Нет ни копий кода для разных окружений, ни общего кода, расшаренного между несколькими приложениями: любое окружение (локальное, staging, prod) — это развёртывание одного и того же репозитория, различающееся только конфигурацией.

### II. Зависимости (Dependencies)

> Явно объявляйте и изолируйте зависимости.

Все зависимости явно объявлены в `package.json` и зафиксированы с точностью до версии в `package-lock.json`; установка через `npm ci` даёт побайтово воспроизводимое дерево `node_modules`. Приложение не полагается на неявное существование системных пакетов: нет вызовов внешних утилит (`curl`, `imagemagick` и т. п.), а единственная системная предпосылка — сам Node.js — зафиксирована в поле `engines` и в базовом образе `node:22-alpine` в Dockerfile.

### III. Конфигурация (Config)

> Храните конфигурацию в переменных окружения.

Всё, что различается между развёртываниями, читается из переменных окружения в одном модуле `src/config.js`: `DATABASE_URL`, `PORT`, `HOST`, `RATE_LIMIT_PER_MINUTE`, `NODE_ENV`. В коде приложения нет ни одного захардкоженного пароля, хоста или порта БД. При отсутствии обязательной переменной приложение падает на старте с внятной ошибкой (fail fast), а не в середине работы. Файл `.env` — только удобство локальной разработки: он в `.gitignore` и не попадает ни в репозиторий, ни в образ; в репозитории лежит шаблон `.env.example` без секретов. Код можно хоть сейчас выложить в открытый доступ, не скомпрометировав ни одно развёртывание — это и есть лакмусовый тест фактора.

Оговорка: в `docker-compose.yml` записаны dev-дефолты учётных данных локальной одноразовой базы (`taskflow`/`taskflow`), публикуемой только на loopback. Это не секрет развёртывания, а значение по умолчанию для локальной разработки, и оно переопределяется переменными окружения (`POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`) — сам compose-файл читает их из окружения или `.env`, так что реальные секреты в репозиторий не попадают.

### IV. Сторонние службы (Backing services)

> Считайте сторонние службы прикреплёнными ресурсами.

Единственная сторонняя служба — PostgreSQL — подключается строго через `DATABASE_URL`. Локальная база, база в docker compose и управляемая облачная база неразличимы для кода: замена одной на другую — это смена строки подключения без единого изменения в коде. Никакой разницы между «локальными» и «сторонними» службами в коде нет.

### V. Сборка, релиз, выполнение (Build, release, run)

> Строго разделяйте стадии сборки и выполнения.

Стадии разделены. **Сборка**: `docker build` (или `npm ci`) собирает артефакт — образ с кодом и зависимостями, конфигурация в него не вшивается. **Релиз**: артефакт соединяется с конфигурацией в момент запуска — `DATABASE_URL` и `PORT` передаются контейнеру через окружение (`docker compose.yml` демонстрирует это явно). **Выполнение**: `node src/server.js` просто запускает готовый релиз. Изменить код в рантайме нельзя — любое изменение требует новой сборки.

### VI. Процессы (Processes)

> Запускайте приложение как один или несколько stateless-процессов.

Приложение — stateless-процесс. Всё постоянное состояние живёт в PostgreSQL. Процесс не хранит ничего между запросами: нет сессий в памяти, нет записи на локальный диск, нет внутрипроцессных кэшей, от которых зависит корректность. Любой запрос может быть обслужен любым экземпляром процесса — «липкие сессии» не нужны. Убить процесс и поднять новый можно в любой момент без потери данных.

### VII. Привязка портов (Port binding)

> Экспортируйте сервисы через привязку портов.

Приложение самодостаточно: Express сам слушает порт из переменной `PORT` и не требует внешнего веб-сервера или контейнера приложений (Apache/Tomcat и т. п.). Оно экспортирует HTTP как сервис и может само выступать сторонней службой для другого приложения — достаточно сообщить тому его URL.

### VIII. Параллелизм (Concurrency)

> Масштабируйтесь с помощью процессной модели.

Благодаря stateless-архитектуре (фактор VI) масштабирование горизонтальное: достаточно запустить N экземпляров процесса за балансировщиком (`docker compose up --scale app=3` после снятия фиксированной привязки порта, или N реплик в оркестраторе). Экземпляры не координируются между собой и не делят память — единственная точка согласования состояния это СУБД, конкурентный доступ к которой обеспечивают транзакции PostgreSQL и пул соединений. Процессы не демонизируются и не пишут pid-файлы — управление ими отдано менеджеру процессов (docker/systemd/оркестратор).

### IX. Утилизируемость (Disposability)

> Максимизируйте надёжность с помощью быстрого запуска и корректного завершения.

Старт — доли секунды (лёгкий стек выбирался в том числе ради этого). По `SIGTERM`/`SIGINT` приложение завершается корректно (`src/server.js`): перестаёт принимать новые соединения, дожидается завершения активных запросов, закрывает пул соединений с БД и выходит; на случай зависших соединений стоит предохранитель — принудительный выход через 10 секунд. Внезапная смерть процесса не ломает данные: каждая операция — одна транзакция в PostgreSQL. Перезапуск упавшего процесса — забота супервизора: в `docker-compose.yml` у сервиса `app` стоит `restart: unless-stopped`, а оркестратор дополнительно опирается на пробы `/api/health` (liveness, без похода в БД — кратковременный сбой БД не приводит к перезапуску здоровых реплик) и `/api/ready` (readiness, с проверкой соединения с БД; именно её использует `HEALTHCHECK` в Dockerfile).

### X. Паритет разработки/продакшена (Dev/prod parity)

> Держите окружения разработки, staging и продакшена максимально похожими.

Везде один и тот же PostgreSQL (а не «SQLite локально, Postgres в проде») и один и тот же код. `docker compose up` поднимает локально ровно ту же связку (postgres:17 + образ приложения + миграции), которая пойдёт в прод. Разрыв инструментов отсутствует; разрыв времени и персонала для учебного проекта минимален по определению: автор и деплоит, и разрабатывает, изменения попадают в развёртывание сразу.

### XI. Логи (Logs)

> Рассматривайте логи как поток событий.

Приложение не управляет файлами логов и не маршрутизирует их: каждый запрос (включая оборванные клиентом — они помечаются `aborted: true` со статусом 499) и каждая ошибка пишутся одной структурированной JSON-строкой в stdout/stderr. Куда этот поток попадёт — в терминал разработчика, в `docker logs`, в ELK/Loki — решает окружение выполнения, а не приложение. Ротация, хранение и анализ — забота платформы.

### XII. Административные процессы (Admin processes)

> Выполняйте задачи администрирования/управления как разовые процессы.

Единственная административная задача — миграции схемы БД — выполняется как разовый процесс `npm run migrate` (он же сервис `migrate` в docker compose, завершающийся после применения). Раннер использует тот же код, те же зависимости и ту же конфигурацию (`DATABASE_URL` из окружения), что и основное приложение, поэтому рассинхронизация исключена. Применённые миграции фиксируются в таблице `schema_migrations`; каждая применяется в транзакции — повторный запуск идемпотентен, а advisory-блокировка PostgreSQL защищает от одновременного запуска двух раннеров (например, при старте нескольких реплик).

## 5. Как проверить

```bash
docker compose up --build        # поднимет БД, применит миграции, запустит приложение
open http://localhost:3000       # фронтенд
curl http://localhost:3000/api/health   # {"status":"ok"}    (liveness)
curl http://localhost:3000/api/ready    # {"status":"ready"} (readiness, с проверкой БД)
npm test                         # юнит- и интеграционные тесты (нужен локальный PostgreSQL)
```

Без Docker — см. раздел «Запуск без Docker» в `README.md`.
