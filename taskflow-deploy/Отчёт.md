## 3. Доработка приложения

### 3.1. Несколько подов: состояние вне пода

TaskFlow не хранит в поде ничего, что нужно сохранить между запросами: проекты и задачи лежат в
PostgreSQL ([k8s/platform/10-postgres.yaml](k8s/platform/10-postgres.yaml)). Поэтому любой запрос
может обработать любая реплика любой версии. Это видно во всех демонстрациях:

* в canary две версии по очереди отвечают на один и тот же `GET /api/projects` и видят одни и те же данные;
* в shadow проект, созданный через 2.1.0, сразу виден в списке.

Обе версии одновременно работают с одной схемой БД. Новая версия при старте применяет миграции,
пока старая ещё обслуживает трафик (init-контейнер `migrate`). Поэтому миграции должны быть
обратно совместимыми (expand/contract): сначала добавить, потом, когда старой версии нет, удалить.

Реплик в каждой стратегии не меньше двух (rolling — четыре). Мягкая `podAntiAffinity` разносит их
по узлам в многоузловом кластере.

### 3.2. Пробы и корректная замена подов

База Deployment — [k8s/app/deployment.yaml](k8s/app/deployment.yaml):

| Механизм | Настройка | Зачем при выкатке |
|---|---|---|
| readinessProbe | `GET /api/ready` (проверяет БД), каждые 3 с | Envoy Gateway берёт адреса из EndpointSlice, и неготовый под туда не попадает: запросы не идут на реплику, которая ещё стартует или потеряла базу |
| livenessProbe | `GET /api/health` (без БД), каждые 10 с | перезапуск зависшего процесса; сбой базы не перезапускает здоровые реплики |
| `preStop: sleep 5` | пауза перед SIGTERM | удаление пода из балансировки и SIGTERM идут параллельно; за 5 с Envoy перестаёт слать запросы на под |
| graceful shutdown | uvicorn дорабатывает начатые запросы до 10 с | ни один принятый запрос не обрывается |
| `minReadySeconds: 5`, `maxUnavailable: 0`, `maxSurge: 1` | RollingUpdate | старая реплика гасится, только когда новая простояла готовой 5 с; ёмкость не проседает ниже 4 реплик |

Пример из [logs/1-rolling.app.log](logs/1-rolling.app.log): последний запрос на старую реплику
`taskflow-857687f6c8-mnm2q` пришёл в `13:42:24.973`, а сервер этой реплики завершился
(`shutting down`) в `13:42:30.261`. Сначала Envoy перестал слать на неё запросы, через 5 с
`preStop` она получила SIGTERM. Ни одного оборванного запроса.

### 3.3. Версия в ответе и в метрике

Версию «вшивает» сборка образа: `docker build --build-arg APP_VERSION=2.2.0`
([Dockerfile](../app/Dockerfile), [taskflow/\_\_init\_\_.py](../app/taskflow/__init__.py)).
Скрипт [scripts/build-images.sh](scripts/build-images.sh) собирает обе версии в minikube.
Версия видна четырьмя способами:

| Где | Как выглядит | Код |
|---|---|---|
| тело ответа | `GET /api/version` → `{"service":"taskflow","version":"2.2.0","instance":"taskflow-canary-…"}` | [app.py](../app/taskflow/app.py) |
| заголовки **каждого** ответа | `X-App-Version: 2.2.0`, `X-Served-By: <имя пода>` | [middleware.py](../app/taskflow/middleware.py) |
| метрика | `taskflow_build_info{version="2.2.0"} 1` на `:9464/metrics` | [metrics.py](../app/taskflow/metrics.py) |
| лог | поле `service.version` в каждой строке, `host` в access-логе | [logger.py](../app/taskflow/logger.py) |

Имя пода приходит из Downward API (`POD_NAME`). Заголовки позволяют без доступа к кластеру
увидеть, куда шлюз направил запрос. Ещё важнее, что Envoy записывает их в свой access-лог
(раздел 4), и распределение трафика по версиям проверяется по журналу шлюза.

`count by (version) (taskflow_build_info)` показывает, сколько реплик какой версии сейчас работает.
Поды ДЗ №8 намеренно не помечены аннотациями `prometheus.io/scrape`: демонстрационный трафик не
должен попадать в SLO прошлых ДЗ. Метрика показана в видео rolling запросом к `/metrics` реплики.

Добавлены тесты: `/api/version`, заголовки на ответах API, ошибки и статики, `host` в логе,
`POD_NAME` в конфигурации, `taskflow_build_info`. Весь набор — **51 тест, все проходят**
(pytest против PostgreSQL 17).

### 3.4. Что пришлось поменять из-за шлюза

* **Лимит запросов.** Приложение ограничивает 600 запросов в минуту на IP клиента. За шлюзом все
  запросы приходят с одного IP — пода Envoy, и 20 запросов/с от всех пользователей уже дают 429.
  В ConfigMap этого стенда лимит поднят до 100 000. Правильное место для лимита — шлюз
  (`BackendTrafficPolicy.rateLimit` по реальному IP клиента).
* **Keep-alive.** uvicorn закрывает простаивающее соединение через 5 с, Envoy держит его час. Если
  Envoy отправит запрос в соединение, которое реплика как раз закрывает, клиент получит 503.
  [BackendTrafficPolicy](k8s/gateway/03-backend-traffic-policy.yaml) ограничивает простой
  соединения Envoy → под 4 секундами, меньше, чем у приложения.

## 4. Envoy Gateway в minikube

По схеме quickstart Envoy Gateway: контроллер ставится из `install.yaml` релиза
([scripts/install-envoy-gateway.sh](scripts/install-envoy-gateway.sh)), дальше цепочка
`GatewayClass eg` → `Gateway eg` → `HTTPRoute`, а снаружи шлюз доступен через
`kubectl port-forward` до Service прокси на `127.0.0.1:8888`, имя хоста — `taskflow.local`.

```
 traffic.py / curl ── Host: taskflow.local ──► 127.0.0.1:8888 (port-forward)
                                                     │
                     envoy-gateway-system            ▼
   ┌──────────────────────────┐  xDS   ┌───────────────────────────┐
   │ envoy-gateway            │ ─────► │ Envoy (Gateway eg, :80)   │── access-лог JSON:
   │ (контроллер Gateway API) │        │ маршруты из HTTPRoute     │   версия, реплика, маршрут
   └──────────────────────────┘        └─────────────┬─────────────┘
                     taskflow-deploy                 │ напрямую на поды из EndpointSlice
            ┌────────────────────────────────────────┼──────────────────────────┐
            ▼                                        ▼                          │
   Service taskflow-<дорожка A> → поды 2.1.0   Service taskflow-<дорожка B> → поды 2.2.0
            └──────────────────────────┬─────────────┘
                                       ▼
                               PostgreSQL db-0 (общая база)
```

| Файл | Что задаёт |
|---|---|
| [k8s/gateway/00-gatewayclass.yaml](k8s/gateway/00-gatewayclass.yaml) | `GatewayClass eg` → контроллер `gateway.envoyproxy.io/gatewayclass-controller` |
| [k8s/gateway/01-envoyproxy.yaml](k8s/gateway/01-envoyproxy.yaml) | параметры прокси: Service типа ClusterIP (в minikube нет балансировщика), ресурсы, **access-лог JSON** с полями `app_version` и `served_by` из заголовков ответа |
| [k8s/gateway/02-gateway.yaml](k8s/gateway/02-gateway.yaml) | `Gateway eg`: HTTP-слушатель на :80, маршруты из своего namespace |
| [k8s/gateway/03-backend-traffic-policy.yaml](k8s/gateway/03-backend-traffic-policy.yaml) | простой соединений к подам ≤ 4 с |

Состояние после [scripts/deploy-platform.sh](scripts/deploy-platform.sh):

```
NAME   CONTROLLER                                      ACCEPTED
eg     gateway.envoyproxy.io/gatewayclass-controller   True
NAME   CLASS   ADDRESS          PROGRAMMED
eg     eg      10.100.241.126   True
```

**Манифесты стратегий** собраны kustomize. [k8s/app/](k8s/app/) — база: один Deployment и
Service `taskflow` (образ 2.1.0). Каждая стратегия в `k8s/strategies/<стратегия>/` берёт базу один
раз (rolling) или дважды, как две дорожки. У дорожки свой суффикс имени, метка `track` (она же в
селекторах Deployment и Service) и тег образа. Например,
[canary/canary/kustomization.yaml](k8s/strategies/canary/canary/kustomization.yaml) даёт
Deployment и Service `taskflow-canary` с образом `taskflow:2.2.0`. Различие стратегий почти целиком
сосредоточено в одном HTTPRoute.

**Как собраны доказательства.** [scripts/traffic.py](scripts/traffic.py) шлёт `GET /api/projects`
(настоящий запрос к API с походом в базу) с постоянной частотой, раскладывает ответы по
`X-App-Version` и раз в секунду печатает строку вида

```
13:42:12  2.1.0 █████···············   5 [2]  2.2.0 ███████████████·····  15 [3]  ошибок 0
```

(ответы версии за секунду и `[число разных реплик]`), а в конце — итог. Независимо от клиента ту
же картину показывает access-лог Envoy (`logs/*.envoy.log`): в нём на каждый запрос записаны
маршрут, реплика и версия, ответившие на него. Время в строках трафика и в логах — UTC.

## 5. Стратегии

### 5.1. Rolling — постепенная замена реплик

**Как устроено.** Один Deployment `taskflow` на 4 реплики ([k8s/strategies/rolling](k8s/strategies/rolling/))
и неизменный HTTPRoute на Service `taskflow`. Версию переключает сам Deployment:

```yaml
minReadySeconds: 5
strategy:
  type: RollingUpdate
  rollingUpdate: {maxUnavailable: 0, maxSurge: 1}
```

**Что сделано.** Под трафиком 20 запросов/с в течение 75 с:

```bash
kubectl -n taskflow-deploy set image deploy/taskflow migrate=taskflow:2.2.0 taskflow=taskflow:2.2.0
kubectl -n taskflow-deploy rollout status deploy/taskflow
```

**Результат.** Выкатка заняла около 40 с. Kubernetes по одной добавлял реплику 2.2.0 и, когда она
5 с простояла готовой, гасил одну 2.1.0. Доля новой версии росла вместе с числом её реплик
(в скобках — сколько разных реплик ответило за секунду):

```
13:41:52  2.1.0 ████████████████████  20 [4]  2.2.0 ····················   0 [0]  ошибок 0
13:41:57  2.1.0 ███████████████·····  15 [3]  2.2.0 █████···············   5 [1]  ошибок 0
13:42:02  2.1.0 ████████············   8 [3]  2.2.0 ████████████········  12 [2]  ошибок 0
13:42:12  2.1.0 █████···············   5 [2]  2.2.0 ███████████████·····  15 [3]  ошибок 0
13:42:17  2.1.0 ███·················   3 [1]  2.2.0 █████████████████···  17 [3]  ошибок 0
13:42:26  2.1.0 ····················   0 [0]  2.2.0 ████████████████████  20 [4]  ошибок 0
Итого: 1500 запросов за 75.0 с, ошибок 0 (0.00 %)
```

По access-логу Envoy: 559 ответов 2.1.0 и 943 ответа 2.2.0 (1500 запросов трафика и 2 curl),
**все 200**. Первый ответ 2.2.0 — в `13:41:52.325`, последний ответ 2.1.0 — в `13:42:24.973`:
около 33 с обе версии обслуживали пользователей одновременно. Запросы распределились по
8 репликам: 4 старым и 4 новым. Логи всех восьми, включая удалённые, — в
[logs/1-rolling.app.log](logs/1-rolling.app.log). `kubectl rollout history` хранит ревизию
`release 2.2.0`, `kubectl rollout undo` вернёт 2.1.0 такой же постепенной выкаткой.

**Вывод.** Стратегия по умолчанию в Kubernetes, без лишних ресурсов (+1 под) и без простоя, если
у приложения правильные пробы и корректное завершение. Минусы: пока идёт выкатка, пользователь
может попасть то на старую, то на новую версию. Долей трафика не управляешь, она равна доле
реплик. Откат — такая же постепенная выкатка, и до её конца ошибка новой версии видна части
пользователей.

### 5.2. Blue/Green — мгновенное переключение и откат

**Как устроено.** Две полные копии по 2 реплики: `taskflow-blue` (2.1.0) и `taskflow-green` (2.2.0)
([k8s/strategies/blue-green](k8s/strategies/blue-green/)). Боевой маршрут смотрит на blue.
Отдельный маршрут `preview.taskflow.local` смотрит на green: новую версию проверяют через тот же
шлюз до переключения.

```yaml
# httproute.yaml                              # httproute-preview.yaml
hostnames: [taskflow.local]                   hostnames: [preview.taskflow.local]
rules:                                        rules:
  - backendRefs:                                - backendRefs:
      - {name: taskflow-blue, port: 80}             - {name: taskflow-green, port: 80}
```

**Что сделано.** Проверка green через preview (`/api/version` → 2.2.0, `/api/projects` → 200).
Затем под трафиком 20 запросов/с переключение одной правкой маршрута, через 12 с откат той же
правкой:

```bash
kubectl -n taskflow-deploy patch httproute taskflow --type=json \
  -p '[{"op":"replace","path":"/spec/rules/0/backendRefs/0/name","value":"taskflow-green"}]'   # переключение
kubectl -n taskflow-deploy patch httproute taskflow --type=json \
  -p '[{"op":"replace","path":"/spec/rules/0/backendRefs/0/name","value":"taskflow-blue"}]'    # откат
```

**Результат.** Access-лог Envoy делится на три непрерывных отрезка без перемешивания версий:

```
2.1.0 160 запросов 13:49:25.665 → 13:49:43.662
2.2.0 243 запросов 13:49:43.710 → 13:49:55.811
2.1.0 238 запросов 13:49:55.854 → 13:50:07.713
```

Переключение заняло **48 мс** между последним ответом blue и первым ответом green, откат — **43 мс**.
Это время, за которое Envoy Gateway перевёл изменённый HTTPRoute в конфигурацию Envoy (xDS).
Все 641 ответ — 200, у клиента `ошибок 0 (0.00 %)`. Поды не пересоздавались: обе копии работали
всё время, поэтому и откат мгновенный.

**Вывод.** Самый быстрый и предсказуемый откат и возможность проверить новую версию целиком до
переключения. Цена — двойные ресурсы на время выкатки. Ещё нужно помнить, что «мгновенно» переходят
все пользователи сразу: ошибку, которую не поймали на preview, увидят все до отката.

### 5.3. Canary — ramp 90/10 → 50/50 → 0/100

**Как устроено.** `taskflow-stable` (2.1.0) и `taskflow-canary` (2.2.0) по 2 реплики
([k8s/strategies/canary](k8s/strategies/canary/)). Долю трафика задают веса в одном правиле HTTPRoute.
Доля = weight / сумма весов, и она **не зависит от числа реплик**:

```yaml
rules:
  - backendRefs:
      - {name: taskflow-stable, port: 80, weight: 90}
      - {name: taskflow-canary, port: 80, weight: 10}
```

Canary только через Deployment (без шлюза) делит трафик пропорционально числу подов: 10 % — это
9 старых реплик на 1 новую. Через Gateway API 10 % получается при любом числе реплик.

**Что сделано.** Три шага. На каждом — правка весов и 12 с трафика по 20 запросов/с:

```bash
kubectl -n taskflow-deploy patch httproute taskflow --type=json -p \
  '[{"op":"replace","path":"/spec/rules/0/backendRefs/0/weight","value":50},
    {"op":"replace","path":"/spec/rules/0/backendRefs/1/weight","value":50}]'      # затем 0 и 100
```

**Результат.**

| Шаг | Веса stable/canary | Ответы 2.1.0 | Ответы 2.2.0 | Доля canary | Ошибки |
|---|---|---|---|---|---|
| 1 | 90 / 10 | 216 | 24 | **10,0 %** | 0 |
| 2 | 50 / 50 | 120 | 120 | **50,0 %** | 0 |
| 3 | 0 / 100 | 0 | 240 | **100 %** | 0 |

Access-лог Envoy, разложенный по шагам, совпадает с тем, что увидел клиент:

```
 216 шаг 1 (90/10) 2.1.0 200
  24 шаг 1 (90/10) 2.2.0 200
 120 шаг 2 (50/50) 2.1.0 200
 120 шаг 2 (50/50) 2.2.0 200
 240 шаг 3 (0/100) 2.2.0 200
```

Envoy делит запросы по весам взвешенно-случайно. На 240 запросах получилось ровно 10 % и 50 %,
на малых выборках возможны отклонения на несколько процентов.

**Вывод.** Новая версия сначала затрагивает малую долю пользователей. Между шагами смотрят на
ошибки и задержки canary отдельно от stable: RED-метрики подов дорожки `track=canary` или access-лог Envoy по `app_version`.
Если что-то не так, вес 0 возвращает весь трафик на stable мгновенно. После 0/100 идёт
продвижение: stable обновляют до 2.2.0, возвращают ему 100 % и удаляют canary. Минусы: ручной (или
автоматизированный — Argo Rollouts, Flagger) процесс по шагам. Пользователь между запросами может
попадать в разные версии, для «липкости» нужна привязка по cookie/заголовку.

### 5.4. A/B — по заголовку на выбранную аудиторию

**Как устроено.** Вариант A `taskflow-a` (2.1.0) и вариант B `taskflow-b` (2.2.0)
([k8s/strategies/ab-testing](k8s/strategies/ab-testing/)). Версия выбирается не случайно, а по
признаку запроса:

```yaml
rules:
  - matches:
      - headers: [{type: Exact, name: X-User-Group, value: beta}]
    backendRefs: [{name: taskflow-b, port: 80}]
  - backendRefs: [{name: taskflow-a, port: 80}]
```

Правило с условием на заголовок точнее правила без условий, поэтому по Gateway API оно
проверяется первым, независимо от порядка в списке.

**Что сделано.** `curl` без заголовка → 2.1.0, с `X-User-Group: beta` → 2.2.0,
с `X-User-Group: staff` → 2.1.0 (не та аудитория). Затем две аудитории одновременно, по
10 запросов/с в течение 12 с.

**Результат.**

```
Итого [все ]: 120 запросов за 12.0 с, ошибок 0 (0.00 %)      2.1.0 120 100.0 %   2.2.0   0
Итого [beta]: 120 запросов за 12.0 с, ошибок 0 (0.00 %)      2.1.0   0           2.2.0 120 100.0 %
```

Access-лог Envoy: аудитория → версия и сработавшее правило маршрута:

```
 121 (нет) → 2.1.0 200        121 httproute/taskflow-deploy/taskflow/rule/0/...  (beta → B)
 121 beta  → 2.2.0 200        122 httproute/taskflow-deploy/taskflow/rule/1/...  (остальные → A)
   1 staff → 2.1.0 200
```

Распределение детерминированное: ни один запрос аудитории не попал в чужой вариант.

**Вывод.** Новая версия достаётся заранее выбранным пользователям (бета-тестерам, сотрудникам,
региону), и каждый пользователь стабильно видит один вариант. Это нужно и для экспериментов
(сравнить метрики A и B), и для раннего доступа. Заголовок здесь проставляет клиент. В
настоящем сервисе признак аудитории выставляет доверенная сторона (аутентификация, cookie от
бэкенда), иначе в бету попадёт любой, кто знает заголовок.

### 5.5. Shadow — зеркалирование копии трафика

**Как устроено.** Пользователям отвечает `taskflow-primary` (2.1.0). Envoy копирует каждый GET в
`taskflow-shadow` (2.2.0), а ответ копии отбрасывает
([k8s/strategies/shadow](k8s/strategies/shadow/httproute.yaml)):

```yaml
rules:
  - matches: [{method: GET}]
    filters:
      - type: RequestMirror
        requestMirror: {backendRef: {name: taskflow-shadow, port: 80}}
    backendRefs: [{name: taskflow-primary, port: 80}]
  - backendRefs: [{name: taskflow-primary, port: 80}]     # POST/PUT/DELETE — без копии
```

Зеркалируются **только GET**. Обе версии пишут в одну базу, и копия `POST /api/projects` создала
бы второй проект, а копия `DELETE` удалила бы повторно. Чтобы зеркалить и изменяющие запросы,
shadow нужна отдельная база или режим «только чтение».

**Что сделано и результат** — четыре проверки:

1. **Клиенты видят только primary.** 200 GET: `2.1.0 — 200 (100 %)`, ошибок 0.
2. **Shadow получила копии.** В логах primary 200 запросов к API, в логах shadow тоже 200. Один и тот
   же `request_id` (его выставляет Envoy) есть в обеих версиях:
   ```
   {"version":"2.1.0","host":"taskflow.local","method":"GET","path":"/api/projects","status":200,"request_id":"269be0fa-94dc-4c58-bb0d-0266a2914c02"}
   {"version":"2.2.0","host":"taskflow.local","method":"GET","path":"/api/projects","status":200,"request_id":"269be0fa-94dc-4c58-bb0d-0266a2914c02"}
   ```
3. **Изменяющие запросы не дублируются.** `POST /api/projects` → 201 от 2.1.0. POST в логах
   primary — 1, в логах shadow — 0, проект с этим именем в базе — ровно один.
4. **Ошибки новой версии не видны пользователям.** В shadow включено внесение сбоев
   `FAULT_ERROR_RATE=0.5` (механизм из ДЗ №5–6). На 200 GET shadow ответила `104 × 200` и
   `96 × 500`, а клиенты получили **200 из 200 успешных ответов от 2.1.0**. В access-логе Envoy за
   всю демонстрацию только `401 GET 2.1.0 200` и `1 POST 2.1.0 201`: ответы копий в журнал запросов
   не попадают.

**Вывод.** Новая версия проходит проверку настоящим трафиком (ошибки, задержки, нагрузка,
совместимость с реальными данными) без какого-либо риска для пользователей. Здесь это видно по
50 % ошибок shadow, которых никто не заметил. Цена: двойная нагрузка на бэкенды и общие зависимости
(база получает каждый читающий запрос дважды). Кроме того, побочные эффекты копий (записи, письма,
платежи) надо отключать. Shadow ничего не выкатывает, это проверка перед canary или blue/green.

## 6. Сравнение

| | Rolling | Blue/Green | Canary | A/B | Shadow |
|---|---|---|---|---|---|
| Кто получает новую версию | все, постепенно | все, сразу | доля по весу | выбранная аудитория | никто (копия) |
| Чем управляется | Deployment | HTTPRoute (имя backend) | HTTPRoute (weight) | HTTPRoute (match по заголовку) | HTTPRoute (RequestMirror) |
| Две версии одновременно | да, во время выкатки | да, вся вторая копия | да | да | да |
| Лишние ресурсы | +1 под (maxSurge) | ×2 на время выкатки | столько, сколько у canary | вариант B | ×2 (shadow) |
| Скорость отката | новая выкатка (`rollout undo`), десятки секунд | мгновенно, одна правка маршрута | мгновенно, вес 0 | мгновенно | не нужен — пользователи не затронуты |
| Риск для пользователей | все видят ошибку новой версии, пока не откатят | все, но откат мгновенный | только доля canary | только аудитория B | нет |
| Когда применять | обычные совместимые релизы | крупные релизы, нужен быстрый откат и проверка до переключения | рискованные изменения, проверка на метриках | эксперименты, бета-функции | проверка производительности и корректности на реальном трафике |

Общее ограничение всех стратегий здесь — **общая база**. Обе версии работают с одной схемой
(нужны совместимые миграции), а shadow не может безопасно зеркалить изменяющие запросы.

## 7. Что пошло не так при подготовке

* **Не хватило ресурсов minikube.** Контейнер minikube был ограничен 2 CPU и 4000 МБ, и в этот
  объём уже упирался стенд прошлых ДЗ (VictoriaMetrics, Victoria Logs, Grafana, Vector). При первой
  пробной выкатке давление памяти на узле дошло до 50 % (PSI). `pg_isready` перестал укладываться
  в таймаут, PostgreSQL перезапустился по liveness, а `/api/ready` у всех реплик стал отдавать 503:
  выкатка встала. Лимиты подняты до 4 CPU и 6 ГБ (`docker update`, в пределах Docker VM на 8 CPU и
  8 ГБ). После этого пробные прогоны всех стратегий прошли без ошибок.
* **Рендер видео и квота CPU «роняли» узел.** Во время записи на хосте работал рендер GIF → MP4
  (agg, ffmpeg), и container runtime в minikube переставал отвечать. Один раз узел на минуту ушёл в
  NotReady (`PLEG is not healthy`), в другой раз в записи canary последняя команда `kubectl` упала
  с `TLS handshake timeout`. Причина — квота CPU контейнера minikube: cgroup набрала 31 000 с
  троттлинга (`throttled_usec`). Что сделано: квота поднята до всех 8 CPU Docker VM;
  [scripts/record.sh](scripts/record.sh) сначала записывает все сценарии (перед каждым ждёт
  готовности узла и API-сервера), а рендерит в конце с `nice` и двумя потоками ffmpeg. Canary
  перезаписана, в итоговых записях ошибок нет.
* **Access-лог Envoy пишется с задержкой.** Envoy сбрасывает файловый лог раз в 10 с, и выборка
  сразу после трафика теряла последние запросы. Сценарии ждут сброса перед чтением журнала.
* **Суффикс `-shadow` у копий.** Envoy по умолчанию дописывает к Host зеркалированного запроса
  `-shadow`, но Envoy Gateway выключает это (`disable_shadow_host_suffix_append: true` в
  config_dump). Копии в логах shadow опознаются по `request_id`, общему с оригиналом.
