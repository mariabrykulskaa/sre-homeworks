Перед приложением стоит Envoy Gateway, всё работает локально в minikube. Старая версия — 2.1.0,
новая — 2.2.0. Во время каждой выкатки на приложение шёл постоянный поток запросов, и я смотрела,

## Что я доработала в приложении

Чтобы приложение нормально работало в нескольких подах, у него не должно быть своего состояния
внутри пода. У меня все данные лежат в PostgreSQL, поэтому на любой запрос может ответить любой
под. Каждая версия запущена минимум в двух экземплярах.

Проверки здоровья:

- **readiness** (`/api/ready`) проверяет, что приложение запустилось и видит базу. Пока проверка
  не прошла, трафик на под не идёт;
- **liveness** (`/api/health`) — если процесс завис, Kubernetes его перезапустит.

Ещё я добавила паузу 5 секунд перед остановкой пода: за это время он успевает выйти из
балансировки и не обрывает запросы.

Версия задаётся при сборке образа: `docker build --build-arg APP_VERSION=2.2.0`. Её видно в ответе
`/api/version`, в заголовке `X-App-Version` у каждого ответа, в метрике `taskflow_build_info` и в
логах. Заголовок `X-Served-By` показывает, какой под ответил.

```
$ curl -H 'Host: taskflow.local' http://127.0.0.1:8888/api/version
{"service":"taskflow","version":"2.1.0","instance":"taskflow-857687f6c8-pbfnd"}
```

## Envoy Gateway

Envoy Gateway 1.9.4 я поставила так же, как в quickstart: GatewayClass, Gateway и HTTPRoute для
приложения ([k8s/gateway/](k8s/gateway/)). Снаружи шлюз открываю через `kubectl port-forward` на
`127.0.0.1:8888`. В настройках прокси включила журнал в JSON, куда попадает версия из ответа: по
нему удобно проверять, куда ушёл каждый запрос.

```
NAME   CONTROLLER                                      ACCEPTED
eg     gateway.envoyproxy.io/gatewayclass-controller   True
NAME   CLASS   ADDRESS          PROGRAMMED
eg     eg      10.100.241.126   True
```

Для трафика я написала небольшой скрипт [traffic.py](scripts/traffic.py). Он шлёт 20 запросов в
секунду и раз в секунду печатает, сколько ответов пришло от каждой версии.

## Rolling

Это обычное обновление Deployment. Подов четыре, Kubernetes меняет их по одному и не убирает
старый, пока новый не готов (`maxUnavailable: 0`, `maxSurge: 1`). Запустила обновление командой
`kubectl set image deploy/taskflow taskflow=taskflow:2.2.0`.

Обновление заняло около 40 секунд. Примерно полминуты отвечали обе версии вперемешку, и доля новой
росла по мере замены подов. Из 1500 запросов ни один не упал.

## Blue/Green

Здесь я развернула обе версии целиком: blue — старую, green — новую. Сначала весь трафик идёт на
blue. Чтобы переключиться, достаточно поменять в HTTPRoute имя сервиса с `taskflow-blue` на
`taskflow-green`. Откат — то же самое в обратную сторону.

В журнале Envoy видно три чётких отрезка: сначала blue, потом green, потом снова blue.

```
2.1.0 160 запросов 13:49:25.665 → 13:49:43.662
2.2.0 243 запросов 13:49:43.710 → 13:49:55.811     ← переключила на green
2.1.0 238 запросов 13:49:55.854 → 13:50:07.713     ← откатила на blue
```

Переключение заняло 48 мс, откат 43 мс, ошибок не было. Откат такой быстрый, потому что старая
версия всё это время продолжала работать.

## Canary

Старая (stable) и новая (canary) версии работают одновременно, а долю трафика задают веса в
HTTPRoute:

```yaml
backendRefs:
  - {name: taskflow-stable, port: 80, weight: 90}
  - {name: taskflow-canary, port: 80, weight: 10}
```

Я прошла три шага: 90/10, 50/50 и 0/100, на каждом по 12 секунд трафика.

| Шаг | Ответов от 2.1.0 | Ответов от 2.2.0 |
|---|---|---|
| 90/10 | 216 | 24 (10 %) |
| 50/50 | 120 | 120 (50 %) |
| 0/100 | 0 | 240 (100 %) |

Доли получились ровно такими, как в настройках, ошибок не было.

## A/B

Здесь новая версия достаётся не случайным запросам, а конкретной аудитории: всем, у кого в запросе
есть заголовок `X-User-Group: beta`. Остальные остаются на старой версии.

```yaml
rules:
  - matches:
      - headers: [{type: Exact, name: X-User-Group, value: beta}]
    backendRefs: [{name: taskflow-b, port: 80}]
  - backendRefs: [{name: taskflow-a, port: 80}]
```

Я запустила две группы одновременно, по 10 запросов в секунду. Все 120 запросов группы beta
попали на 2.2.0, все 120 обычных — на 2.1.0.

## Shadow

Пользователям отвечает старая версия, а Envoy параллельно отправляет копию каждого запроса в новую
и выбрасывает её ответ. Так новую версию можно проверить на настоящем трафике, и пользователи
ничего не заметят.

```yaml
rules:
  - matches: [{method: GET}]
    filters:
      - type: RequestMirror
        requestMirror: {backendRef: {name: taskflow-shadow, port: 80}}
    backendRefs: [{name: taskflow-primary, port: 80}]
  - backendRefs: [{name: taskflow-primary, port: 80}]
```

Копирую только GET-запросы. Обе версии работают с одной базой, и копия POST создала бы, например,
второй такой же проект.

Что получилось:

- клиенты получили все 200 ответов от 2.1.0;
- в логах новой версии те же 200 запросов с теми же `request_id`;
- POST выполнился один раз, до новой версии он не дошёл;
- потом я специально включила в новой версии 50 % ошибок. Она стала отвечать 500 почти на половину
  копий, но у клиентов ошибок так и не появилось.
