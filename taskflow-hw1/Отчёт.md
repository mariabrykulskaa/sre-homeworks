# Отчёт: TaskFlow — приложение 12 факторов

Исходный код — [../app](../app) (Python), инструкция по запуску — [../app/README.md](../app/README.md).

## 1. Доменная область

**TaskFlow** — трекер задач по проектам. Пользователь создаёт проекты, внутри каждого проекта ведёт задачи, двигает их по статусам (`к работе → в работе → готово`), фильтрует по статусу, редактирует и удаляет. Доменная область выбрана намеренно компактной: она даёт содержательные CRUD-операции и связь «один-ко-многим» между сущностями, но не перегружает приложение логикой — это пригодится для последующих домашних заданий (контейнеризация, балансировка, масштабирование).

## 2. Стек реализации

| Слой | Технология | Почему |
|---|---|---|
| Бэкенд | Python 3.13 + FastAPI, сервер uvicorn | Лёгкий асинхронный стек, мгновенный старт, REST и автодокументация API (`/docs`) «из коробки» |
| Протокол | HTTP/1.1, REST, JSON | По рекомендации из задания (без gRPC — не будет проблем с балансировкой) |
| СУБД | PostgreSQL 17 | По требованию задания; доступ через `psycopg 3` с пулом соединений (`psycopg_pool`) и параметризованными запросами |
| Фронтенд | HTML + CSS + ванильный JavaScript | SPA на одной странице без сборки — минимум ресурсов и зависимостей |
| Миграции | Собственный раннер (`python -m taskflow.migrate`) | SQL-файлы, журнал в таблице `schema_migrations`, транзакционное применение |
| Контейнеризация | Dockerfile + docker compose | Одинаковое окружение локально и в проде |
| Тесты | pytest | Юнит-тесты валидации, сбоев, логгера + интеграционные тесты API против тестовой БД |

Зависимостей шесть, все зафиксированы до версии в [`requirements.txt`](../app/requirements.txt): `fastapi`, `uvicorn`, `psycopg[binary]`, `psycopg-pool`, `prometheus-client`, `python-dotenv`. Шрифты фронтенда самостоятельно хостятся в `public/fonts/` — у приложения нет недекларированных внешних зависимостей времени выполнения (CDN и т. п.).

## 3. Основные сущности

### Project (проект)

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | BIGINT IDENTITY | первичный ключ |
| `name` | TEXT | 1–120 символов, обязательное |
| `description` | TEXT | до 2000 символов |
| `created_at`, `updated_at` | TIMESTAMPTZ | ставятся автоматически |

### Task (задача)

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | BIGINT IDENTITY | первичный ключ |
| `project_id` | BIGINT | FK → `projects.id`, `ON DELETE CASCADE` |
| `title` | TEXT | 1–200 символов, обязательное |
| `description` | TEXT | до 5000 символов |
| `status` | TEXT | `todo` / `in_progress` / `done` (CHECK-ограничение) |
| `created_at`, `updated_at` | TIMESTAMPTZ | ставятся автоматически |

Связь: один проект — много задач. Все ограничения продублированы на двух уровнях: валидация на входе в API ([`taskflow/validate.py`](../app/taskflow/validate.py)) и ограничения СУБД (CHECK, FK, NOT NULL) в [`migrations/001_init.sql`](../app/migrations/001_init.sql).

Над обеими сущностями реализован полный CRUD (см. таблицу эндпоинтов в [`app/README.md`](../app/README.md)): маршруты — [`taskflow/routes/projects.py`](../app/taskflow/routes/projects.py) и [`taskflow/routes/tasks.py`](../app/taskflow/routes/tasks.py).

## 4. Соответствие 12 факторам

### I. Кодовая база (Codebase)

> Одна кодовая база в системе контроля версий — много развёртываний.

Весь код (бэкенд, фронтенд, миграции, инфраструктурные файлы) живёт в одном git-репозитории, в каталоге `app/`. Нет ни копий кода для разных окружений, ни общего кода, расшаренного между несколькими приложениями: любое окружение (локальное, docker compose, minikube) — это развёртывание одного и того же кода, различающееся только конфигурацией.

### II. Зависимости (Dependencies)

> Явно объявляйте и изолируйте зависимости.

Все зависимости явно объявлены в `requirements.txt` с точными версиями (`fastapi==0.115.12` и т. д.), инструменты разработки — отдельно в `requirements-dev.txt`. Установка `pip install -r requirements.txt` в изолированное окружение (venv или образ) даёт одно и то же дерево пакетов. Приложение не полагается на неявное существование системных пакетов: нет вызовов внешних утилит (`curl`, `psql` и т. п.); драйвер PostgreSQL ставится с собственной libpq (`psycopg[binary]`), а сама версия Python зафиксирована базовым образом `python:3.13-slim` в Dockerfile.

### III. Конфигурация (Config)

> Храните конфигурацию в переменных окружения.

Всё, что различается между развёртываниями, читается из переменных окружения в одном модуле [`taskflow/config.py`](../app/taskflow/config.py): `DATABASE_URL`, `PORT`, `HOST`, `RATE_LIMIT_PER_MINUTE`, `APP_ENV`, `METRICS_PORT` и др. В коде нет ни одного захардкоженного пароля, хоста или порта БД. При отсутствии обязательной переменной или неверном значении приложение падает на старте с внятной ошибкой (fail fast), а не в середине работы. `load_config()` — чистая функция от словаря окружения, поэтому её легко проверить тестами. Файл `.env` — только удобство локальной разработки: он в `.gitignore` и `.dockerignore`, не попадает ни в репозиторий, ни в образ; в репозитории лежит шаблон `.env.example` без секретов. Код можно хоть сейчас выложить в открытый доступ, не скомпрометировав ни одно развёртывание — это и есть лакмусовый тест фактора.

Оговорка: в `docker-compose.yml` записаны dev-дефолты учётных данных локальной одноразовой базы (`taskflow`/`taskflow`), публикуемой только на loopback. Это не секрет развёртывания, а значение по умолчанию для локальной разработки, и оно переопределяется переменными окружения (`POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`).

### IV. Сторонние службы (Backing services)

> Считайте сторонние службы прикреплёнными ресурсами.

Единственная сторонняя служба — PostgreSQL — подключается строго через `DATABASE_URL` ([`taskflow/db.py`](../app/taskflow/db.py)). Локальная база, база в docker compose и управляемая облачная база неразличимы для кода: замена одной на другую — это смена строки подключения без единого изменения в коде.

### V. Сборка, релиз, выполнение (Build, release, run)

> Строго разделяйте стадии сборки и выполнения.

Стадии разделены. **Сборка**: `docker build` собирает артефакт — образ с кодом и зависимостями, конфигурация в него не вшивается. **Релиз**: артефакт соединяется с конфигурацией в момент запуска — `DATABASE_URL` и `PORT` передаются контейнеру через окружение (`docker-compose.yml`, позже — ConfigMap и Secret в Kubernetes). **Выполнение**: `python -m taskflow.server` просто запускает готовый релиз. Изменить код в рантайме нельзя — любое изменение требует новой сборки.

### VI. Процессы (Processes)

> Запускайте приложение как один или несколько stateless-процессов.

Приложение — stateless-процесс. Всё постоянное состояние живёт в PostgreSQL. Процесс не хранит ничего между запросами: нет сессий в памяти, нет записи на локальный диск (в Kubernetes файловая система контейнера и вовсе только для чтения), нет внутрипроцессных кэшей, от которых зависит корректность. Любой запрос может быть обслужен любым экземпляром процесса — «липкие сессии» не нужны. Убить процесс и поднять новый можно в любой момент без потери данных.

### VII. Привязка портов (Port binding)

> Экспортируйте сервисы через привязку портов.

Приложение самодостаточно: встроенный ASGI-сервер uvicorn сам слушает порт из переменной `PORT` и не требует внешнего веб-сервера (nginx, Apache и т. п.). Приложение экспортирует HTTP как сервис и может само выступать сторонней службой для другого приложения — достаточно сообщить тому его URL.

### VIII. Параллелизм (Concurrency)

> Масштабируйтесь с помощью процессной модели.

Благодаря stateless-архитектуре (фактор VI) масштабирование горизонтальное: достаточно запустить N экземпляров процесса за балансировщиком (N реплик Deployment в Kubernetes). Экземпляры не координируются между собой и не делят память — единственная точка согласования состояния это СУБД, конкурентный доступ к которой обеспечивают транзакции PostgreSQL и пул соединений. Внутри процесса запросы обслуживаются асинхронно (asyncio), так что один процесс держит много одновременных соединений. Процессы не демонизируются и не пишут pid-файлы — управление ими отдано менеджеру процессов (docker/оркестратор).

### IX. Утилизируемость (Disposability)

> Максимизируйте надёжность с помощью быстрого запуска и корректного завершения.

Старт — около секунды. По `SIGTERM`/`SIGINT` uvicorn перестаёт принимать новые соединения, дожидается завершения активных запросов (не дольше 10 секунд — `timeout_graceful_shutdown`), затем в обработчике остановки (lifespan в [`taskflow/app.py`](../app/taskflow/app.py)) закрывается пул соединений с БД, и процесс выходит с кодом 0. Внезапная смерть процесса не ломает данные: каждая операция — одна транзакция в PostgreSQL. Перезапуск упавшего процесса — забота супервизора: в `docker-compose.yml` у сервиса `app` стоит `restart: unless-stopped`, а оркестратор дополнительно опирается на пробы `/api/health` (liveness, без похода в БД — кратковременный сбой БД не приводит к перезапуску здоровых реплик) и `/api/ready` (readiness, с проверкой соединения с БД; её же использует `HEALTHCHECK` в Dockerfile).

### X. Паритет разработки/продакшена (Dev/prod parity)

> Держите окружения разработки, staging и продакшена максимально похожими.

Везде один и тот же PostgreSQL 17 (а не «SQLite локально, Postgres в проде») и один и тот же код и образ. `docker compose up` поднимает локально ровно ту же связку (postgres:17 + образ приложения + миграции), которая пойдёт в кластер. Интеграционные тесты тоже идут против настоящего PostgreSQL. Разрыв инструментов отсутствует; разрыв времени и персонала для учебного проекта минимален по определению: автор и деплоит, и разрабатывает.

### XI. Логи (Logs)

> Рассматривайте логи как поток событий.

Приложение не управляет файлами логов и не маршрутизирует их: каждый запрос (включая оборванные клиентом — они помечаются `aborted: true` со статусом 499) и каждая ошибка пишутся одной структурированной JSON-строкой в stdout ([`taskflow/logger.py`](../app/taskflow/logger.py), [`taskflow/middleware.py`](../app/taskflow/middleware.py)). Сообщения библиотек (uvicorn) перенаправлены в тот же JSON-поток. Куда этот поток попадёт — в терминал разработчика, в `docker logs`, в Victoria Logs — решает окружение выполнения, а не приложение. Ротация, хранение и анализ — забота платформы.

### XII. Административные процессы (Admin processes)

> Выполняйте задачи администрирования/управления как разовые процессы.

Единственная административная задача — миграции схемы БД — выполняется как разовый процесс `python -m taskflow.migrate` ([`taskflow/migrate.py`](../app/taskflow/migrate.py)); в docker compose это сервис `migrate`, завершающийся после применения. Раннер использует тот же код, тот же образ и ту же конфигурацию (`DATABASE_URL` из окружения), что и основное приложение, поэтому рассинхронизация исключена. Применённые миграции фиксируются в таблице `schema_migrations`; каждая применяется в транзакции — повторный запуск идемпотентен, а advisory-блокировка PostgreSQL защищает от одновременного запуска двух раннеров (например, при старте нескольких реплик).

## 5. Как проверить

```bash
cd ../app
docker compose up --build                 # поднимет БД, применит миграции и запустит приложение
open http://localhost:3000                # фронтенд
open http://localhost:3000/docs           # документация API (FastAPI)
curl http://localhost:3000/api/health     # {"status":"ok"}    (liveness)
curl http://localhost:3000/api/ready      # {"status":"ready"} (readiness, с проверкой БД)
python -m pytest                          # тесты (нужен PostgreSQL, см. app/README.md)
```
